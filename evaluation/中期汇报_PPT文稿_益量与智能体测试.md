## P4 问题出在哪里：两条链错位

**本页标题建议**：先讲问题，再讲项目名

**核心一句话（可放页首大字）**

> 政府花钱买了「上门探访」，但最后验收时，往往只能证明**「去过了」**，很难证明**「发现了什么、转介了吗、问题处理了吗」**。

**两条链（本页主图，建议左右对照）**

| | **现场真实发生的链（政策要求）** | **最后汇总/验收常用的链（现实）** |
|---|----------------------------------|-------------------------------------|
| **记什么** | 上门 → 发现风险或需求 → 记录 → 转介 → 跟进 → 是否处置 | 完成探访 **N 次** · 时长 · 照片/签到 |
| **能回答什么** | 发现了几个需求？转介了几个？几个闭环？几个还在办？ | 本月探访覆盖率多少？ |
| **卡在哪里** | 信息在一线人员脑子里、在微信里、在表里，**口径还不统一** | 主管月底**手工拼表**给街道验收，缺字段就**退回** |

**三个具体后果（听众一听就懂）**

1. **验收难**：街道要「转介回执日期」「单次服务成本」等字段，现场只拍了照片没登记 → 整行作废。  
2. **说不清成果**：写了「探访 100 人次」，回答不了「发现并推动解决了什么」。  
3. **钱难算账**：不同社区、不同机构字段不一致 → **单位成本无法横向比较**，下一周期预算只能拍脑袋。

**状态标注**：政策要求探访含识别、转介、衔接 → **F 事实**；机构拼表痛苦程度 → **H，待 5 次访谈验证**。

**讲稿要点（30 秒）**：问题不是「老人没人管」，而是「政府已经买了服务，但**买完之后说不清买对了没有**」。这就是两条链的错位。

## P5 益量是什么：解决什么、起什么作用

**本页标题建议**：益量 · 我们到底做什么

**基本信息（页眉小字）**

| 名称 | 益量（课程工作名） | 赛道 | 挑战杯 · 社会治理和公共服务 |
|------|-------------------|------|---------------------------|
| 场景 | 政府购买的**特殊困难老年人探访关爱** | 阶段 | 中期：问题已厘清；**未签约试点** |

**我们解决的一个问题（对齐 P4）**

把分散在 Excel、微信、纸质表里的**服务过程**，整理成一条可核对、可汇总的**成果证据链**：

```text
探访（活动）→ 发现需求/风险（产出）→ 转介与跟进（过程）→ 可提交的验收材料（证据）
```

**起什么作用（分角色，各一句话）**

| 对谁 | 作用 | 举例 |
|------|------|------|
| **项目主管** | 少花几周手工拼表，一眼看到**缺什么字段、哪条没闭环** | 月底不再从 6 个微信群翻照片对 Excel |
| **街道/民政（购买方）** | 验收时看得懂**做了什么、证明在哪**，拨付更有依据 | 按统一模板导出，而不是各机构各一套表 |
| **机构自身** | 不同社区站点**口径一致**，能算**单次服务成本** | 东片写「时长」、西片写「分钟」→ 统一成可比对数据 |
| **下一周期预算** | 有过程数据支撑**「钱花在哪儿、效率如何」**的讨论 | 不是证明「省钱 30%」，而是先能**可比、可审计** |

**明确不是什么（避免听成志愿者项目）**

| ❌ 不是 | ✅ 而是 |
|---------|---------|
| 志愿者撮合 / 量化志愿者工时 | 政府**已付费购买**的专业探访服务的过程与成果管理 |
| 老人预约 App | 机构内部与验收方向的**台账与证据**工具 |
| 证明「老人更幸福」「医疗费下降」 | 先证明**服务过程可追溯、验收材料可生成**（长期影响 **无依据不宣称**） |

**讲稿要点**：有人会问「是不是量化志愿者？」——不是。志愿者是另一套逻辑；我们关注的是**政府招标、机构履约、街道验收**这条链上，「过程」和「可验收成果」之间的断层。

| 依据 | 说了什么 | 和益量的关系 |
|------|----------|--------------|
| 《政府购买服务管理办法》 | 按**数量、质量**付费，强调绩效与预算 | 买服务 ≠ 只数次数，要能说明质量与依据 |
| 《特殊困难老年人探访关爱服务指导意见》 | 探访含需求识别、风险发现、**转介衔接**、隐私保护 | 对应 P4「完整链条」的政策来源 |
| 公开采购案例① | 某市探访关爱项目预算 **42.31 万元**（建档、巡访、需求分析、资源衔接） | 证明**这类服务真被政府购买** |

## P7 一个小例子 + 场域角色（把问题落到数字）

**本页上半：模拟情景里问题怎么发生（S，课程设定）**

| 设定项 | 数值 |
|--------|------|
| 服务机构 | 1 家 · 下辖 2 个社区站点 |
| 服务对象 | 约 **100** 名重点老人（独居/空巢等） |
| 服务要求 | 每人每月至少上门 **1** 次 |
| 一线人员 | **4–6** 人 · 项目主管 **1** 人 |
| 年探访量（粗算） | 100 人 × 12 月 ≈ **1 200 次/年** |

**一次验收困境（具体故事，可口述）**

```text
3 月：探访员在微信发现老人燃气软管老化，发了照片，但没按表登记「异常+转介」
6 月：街道验收，要求每条异常有「转介回执日期」→ 这条不算数，整表被标红退回
主管：从 2 个社区、4 个微信群、3 份 Excel 手工对了 2 周
```

→ 这就是 P4「两条链错位」在 **100 人规模**下的样子。（机构是否普遍如此：**H，访谈验证**）

**本页下半：场域里有哪些人（不预设谁一定用益量）**

| 角色 | 干什么 | 和问题的关系 |
|------|--------|--------------|
| 老人 | 被探访对象 | 不直接操作任何系统 |
| 一线社工/养老员 | 上门、记录、转介 | 信息第一手来源，最怕多填表 |
| 项目主管 | 派单、拼材料、应对验收 | **拼表痛点最可能集中在这里（H）** |
| 街道/民政 | 买服务、验收、付钱 | 要看汇总与证据；**会否用新工具：H** |
| 我们团队 | 4 人学生，本学期 **≤5 次**访谈 | 验证 H，不宣称已合作 |

**三个主体，三个问题（页脚）**

```text
谁最痛？（机构主管 vs 一线）  →  待访谈
谁会用？（主管 vs 街道）      →  待访谈
谁付钱？（机构 / 政府 / 基金会）→  待访谈，中期不写死
```

**讲稿要点**：用 1200 次/年和「燃气软管」故事，让听众明白——我们不是在做「量化志愿者」，而是在解决「**1200 次探访里，有多少次能变成验收认可的一条有效记录**」。

## P10 为什么这样测是合理的：四个原则

**本页要点**

1. **同一项目、同一世界**  
   用《YL-Scenario Ground Truth》冻结益量场域；避免 V1 聊成「志愿者 App」、V2 聊成「助餐平台」——否则无法对比。

2. **信息分层，测「会不会问」**  
   公开背景 vs Hidden State：模拟用户**只有被问对才透露**细节；测澄清能力，不是测背稿。

3. **冲突注入，测「会不会权衡」**  
   例如：主管要详细 vs 一线怕多填；政府买服务 ≠ 政府买我们的工具——看智能体能否守住证据边界。

4. **前后对照，测「有没有真进步」**  
   V1 冻结问题清单 → 改智能体 → **同一套题**再跑；不挑最好的一次 run 汇报。

**讲稿要点**：这和软件回归测试一样：固定输入、固定环境、记录输出、版本对比。我们是在给 **Agent 做 harness（评测束具）**。

## P14 测试执行：.harness 与流程

**本页要点**

**执行方式**

- 通过脚本调用 BDSC 对话 API（如 `run_v1fix_b_dp.py`），非手工点 UI，保证可复现。  
- **模拟用户**：按 Hidden Mapping 规则回答；语义未命中不得泄露隐藏包。  
- **会话隔离**：不同 run 使用不同 `conversation_id`；YL-R 每轮新会话。

**已完成的轮次（V1fix-A，探索性）**

| 类别 | 规模 |
|------|------|
| 益量正式轮次 | 9 个会话 / **36** 轮正式对话 |
| 含教师 T1–T3 | 合计 **12** 会话 / **41** 轮 |
| 模型环境 | 曾混用模型、API 不稳定；结果**保留但标注为探索性** |

**进行中（V1fix-B，确认性）**

- API 与模型固定；每轮记录实际模型  
- 修 harness「零匹配仍泄露 Hidden」等 bug 后重跑  
- 目标：约 7 会话 / ≤34 轮，作为 **V1 正式冻结基线**

**讲稿要点**：V1fix-A 像「试跑发现仪表有问题」；V1fix-B 才是「正式计时」。

## P15 V1fix-A 测试结果（一）：整体印象

**本页要点**

**环境说明（必读）**  
探索性运行；存在模型切换未逐轮记录、个别会话网络污染剔除等情况——**数字供趋势判断，正式分数以 V1fix-B 为准**。

**做得好的地方**

| 方面 | 表现 |
|------|------|
| 基础辅导能力 | 能讲政策逻辑、项目收敛方向 |
| 安全底线 | 压力场景下对**明显编造**有一定拒绝 |
| 用户纠正后 | 部分轮次能吸收学生反驳并调整 |

**粗略工程观测**

- 约 **11–12 次**模型调用 / 用户轮（冻结日志统计）  
- 端到端延迟中位数约 **152 秒/轮**（与多维度并行编排相关）

**讲稿要点**：肯定「能聊」，但中期重点转向「聊得稳、聊得准、聊得快」。

## P16 V1fix-A 测试结果（二）：反复出现的问题

**本页要点（= V2 优化契约的输入）**

| 优先级 | 问题 | 典型表现 |
|--------|------|----------|
| P0 | **数字/事实编造** | 正常建议里凭空出现价格、规模、覆盖率（比压力测试更严重） |
| P0 | **最终总结漂移** | 多轮已收窄到「探访台账」，总结又变成语音/微信工具或换付费方 |
| P1 | **RAG 污染** | 检索命中无关案例（如其他赛道项目），干扰建议 |
| P1 | **提问泛滥** | YL-G 24/24 轮存在「一问多叠」，且常跨主题 |
| P2 | **延迟高** | 多维度 Path A/B 即使用户只问一个小点也可能跑满链路 |
| P2 | **遥测不全** | 对话 JSON 未稳定记录每轮实际模型 |

**初步评分趋势（0–4，探索性）**

| 测试 | Outcome 大致区间 |
|------|------------------|
| YL-G 三轮 | 约 **0–1**（收敛差、漂移多） |
| YL-S 压力 | 约 **3**（显性编造能挡一部分） |
| 理论/概念类 | 约 **2** |

**讲稿要点**：问题在多条测试里**重复出现**，所以适合写进「优化契约」，而不是怪某一次 prompt 手滑。

## P17 从测试到改进：我们准备优化什么（框架稿）

> ⏳ **本节待组内填入 V1fix-B 后定稿**；以下为实现方向框架，汇报时可讲「计划」。

**本页要点**

**智能体层（V2 内容优化，示例）**

- 提示词：证据边界、F/H/S 强制区分、总结前核对 `decisions`  
- 知识库：减少无关案例召回；探访/公益/政务分类  
- 拒绝策略：未验证数字、付费方、长期影响  

**编排层（减法式升级，不新增「世界状态 Agent」）**

| 方向 | 做法 |
|------|------|
| 共享状态 | `Project Runtime State`：memory / progress / **decisions** / tasks |
| 响应契约 | 综合前注入 `must_preserve`、`forbidden_upgrade` |
| 少调用 | 合并维度、按 `refresh` 跳过无关 KG/超图 |
| 快慢路径 | 关键回答先返回，重型面板后台刷新 |

**启用策略**：**影子验证**（用 V1 日志重放新判断）→ 再小流量真启用（见前期讨论）

**讲稿要点**：优化不是「再加功能」，而是「加控制平面 + 减无效调用」；等 V1fix-B 冻结后再报具体 commit 与对比数字。

## P20 总结：中期我们证明了什么

**本页要点**

1. **项目**：益量选题有政策与采购锚点，问题表述清楚，证据边界自律。
