## P3 益量是个什么样的题（为什么说它「复杂」）

**本页要点**

| 维度 | 复杂在哪 |
|------|----------|
| **制度** | 政府购买服务：既要数「做了多少次」，也要说明「做得怎么样」——两条标准同时存在 |
| **业务** | 一次上门探访不是签个到：可能要发现风险、转介社区或医院、再跟进有没有处理 |
| **角色** | 老人、一线社工、机构主管、街道民政——**谁痛、谁用、谁付钱可能是四个人** |
| **证据** | 能把话说清的东西（政策 F）和还没验证的东西（访谈 H）必须分开，不能混写 |
| **赛道** | 挑战杯 · 社会治理和公共服务；工作名 **益量**（课程用，非已上市产品） |

**一句话定位**  
帮政府购买的「探访关爱」项目，把**分散的过程记录**变成**能验收、能核对**的材料——不是老人预约 App，也不是志愿者撮合。

**讲稿**：先让听众知道——这不是「做个养老小程序」，而是卡在「政府买服务之后怎么记账、怎么验收」这条缝上。

## P4 一个故事：问题出在哪（两条链）

**本页建议**：少表格，大口述；幻灯片只放 3～4 行字 + 一张对比图。

**故事（可直接当讲稿）**

> 街道通过政府购买，把「上门看望独居老人」交给一家社区机构。  
> 探访员小李每个月要去几十户人家：看看煤气安不安全、药够不够、要不要联系社区医生。  
> 3 月他在老人家里发现燃气软管老化，顺手在**工作微信群**里发了张照片。  
> 到了 6 月要验收，主管王姐要把三个月的记录交给街道——街道的表上要写：有没有异常、转介给了谁、**回执哪天到的**、这次服务**成本多少**。  
> 小李那次只有照片，表上没登记。街道电脑里这一行被标红：**不算有效记录**。  
> 王姐只好从 **2 个社区站、好几个群、好几份 Excel** 里把同一件事翻出来，对了两周。

**听众只需记住一个反差**

```text
小李脑子里、微信里的那条「完整故事」
          ≠
街道验收表上认的那一行「合格记录」
```

这就是**两条链**：  
- **现场链**：去过 → 发现问题 → 记下来 → 转出去 → 跟到底  
- **验收链**：探访几次、时长多少、材料齐不齐  

政策要求前者（**F**），很多机构月底在拼后者；拼得有多痛苦——我们还在访谈里问（**H**）。

**讲稿收尾**：问题不是「老人没人管」，而是「钱已经花了，但**花得是否清楚、能否验收**说不清」。

## P5 问题规模：用一组数字建立直觉

**本页要点（数字墙，建议做成一页信息图）**

**A. 这个市场是真的（公开采购，F）**

| 案例 | 数字 |
|------|------|
| 某地「特殊困难老年人探访关爱」采购 | 预算约 **42.31 万元** |
| 同类项目（6 个月合同） | **67 万元** |
| 某街道「购买社区服务」（12 个村社，2 年） | 约 **360 万元** |

→ 说明：政府**真花钱买**探访与社区服务；**不等于**政府会买我们的软件（**H**）。

**B. 课程里我们用来讨论的「缩小版现场」（模拟设定 S）**

| 项 | 数字 |
|----|------|
| 服务机构 | 1 家，2 个社区站点 |
| 重点探访对象 | 约 **100** 人 |
| 频次 | 每人每月至少 **1** 次上门 |
| 一年探访量（粗算） | **≈ 1 200 次** |
| 一线人员 | **4–6** 人；主管 **1** 人 |
| 我们团队 | **4** 人；本学期访谈上限 **5** 次 |

**C. 规模带来的管理压力（逻辑推导，非实测）**

| 推导 | 含义 |
|------|------|
| 1 200 次/年 | 若每次只记「去过」，丢一次异常就可能少一条验收证据 |
| 2 个站点字段不一致 | 东片写「时长」、西片写「分钟」→ 汇总时要人工对齐 |
| 街道验收常见要求 | 对象编号、日期、异常、转介、**回执日期**、**单次成本**、佐证链接——缺一项可整行退回 |

**讲稿**：42 万、360 万说明「大钱在政府购买」；100 人、1200 次说明「哪怕一个小点，记录量也不小」——益量要对付的是**规模 × 口径 × 验收**叠加起来的麻烦。

## P6 益量要解决什么、明确不解决什么

**解决什么（对齐 P4 故事）**

```text
把「微信 + Excel + 脑子里的故事」
        ↓
收成一条能交给街道核对的路径：
探访 → 发现 → 转介 → 跟进 → 验收字段齐全
```

| 对谁 | 有什么用 |
|------|----------|
| 机构主管 | 少手工拼表，知道哪条缺材料、哪条没闭环 |
| 街道 | 验收时看得懂、退件少 |
| 机构自己 | 各站点口径一致，**单次成本可以比** |

**不解决什么**

- ❌ 量化志愿者、撮合志愿时长  
- ❌ 老人手机端预约  
- ❌ 证明「孤独感下降」「医疗费节省 X%」（无测量就不写）  

**中期状态**：问题场域和证据边界已厘清；**无签约试点、无付费客户**。

# 第二部分 · 智能体：要应付什么现象

---

## P7 题这么复杂，Agent 用着会出现什么现象

**本页要点**：从「学生带益量去聊 BDSC」的真实体验，引出**必须测试**。

我们用平台三类模式做项目：**课程辅导 / 项目教练 / 竞赛评审**。益量这种题一进去，Agent 容易出现：

| 现象 | 具体表现 | 为什么和「题复杂」有关 |
|------|----------|------------------------|
| **说着说着项目变了** | 本来聊探访台账，总结里出现老人微信端、语音客服 | 多角色、多边界，Agent 易往「常见养老 App」套 |
| **数字随口就来** | 没访谈过就写市场规模、合同额、覆盖率 | 政务题缺数据，模型爱「填空」 |
| **证据分不清** | 把「政府买探访服务」说成「政府要买我们系统」 | F 和 H 混在一起就过不了合规 |
| **问了很多却不推进** | 一轮堆付费方、竞品、问卷、助餐 | 里程碑多，Agent 不知道当前该推进哪一步 |
| **很慢** | 问一句小事，等两分多钟 | 编排里多维度、RAG、超图并行跑满 |

**所以我们做的不是「聊几轮感觉好不好」**，而是：**固定益量这个世界，看 V1 智能体在上述现象上有多严重**——再改、再测、再对比。

**讲稿**：项目越复杂，越不能靠印象评价 Agent；要先有现象清单，再有测试清单。

## P8 测的是谁：V1 基线 vs 以后的 V2

| 名称 | 是什么 | 不是什么 |
|------|--------|----------|
| **V1** | 当前 BDSC 智能体（提示词 + 知识库 + 编排）的第一版基线 | 益量产品 v1.0 |

**中期目标**：用同一套测试冻结 V1 的问题 → 改 Agent → 用**同一套题**证明 V2 更好。

## P9 测试分几类、每类目的是什么

| 类别 | 包含什么 | 目的（一句话） |

## P10 每类测试怎么设计、为什么这样设计

### A. 教师测试 T1–T3

| 项 | 设计 | 为什么 |
|----|------|--------|
| 内容 | 教师规定的统一任务各 1 套 | 与全班同基准，证明平台基本可用 |
| 模式 | T1 辅导 / T2 教练 / T3 竞赛 | 对应 BDSC 三种 `mode` |
| 局限 | 不是益量专用场景 | **不能代替** YL 套——题目通用、世界未冻结 |

### B1. YL-L（课程辅导 · 4 轮固定脚本）

| 项 | 设计 | 为什么 |
|----|------|--------|
| 轮次 | 4 轮，每轮学生发言**固定** | 可复现；比自由聊天少随机 |
| 任务 | 从项目卡片 → MVP 边界 → 验收 vs 成本优先级 → 8 周里程碑 | 测能否按**里程碑顺序**推进 |
| 模式 | `coursework` | 对应学生第一接触项目 |

### B2. YL-G（项目教练 · 3 runs × 最多 8 轮）★ 最重要

| 项 | 设计 | 为什么 |
|----|------|--------|
| 轮次 | 3 次独立 run，每次新会话，**模拟用户**按规则回答 | 测多轮**收敛**；避免一次运气好 |
| 开场 | 只给**公开背景**（100 人、无试点、5 次访谈上限等） | 测 Agent **会不会主动问** |
| Hidden | H01–H10：**问对才透露**（流程、验收字段、预算上限等） | 测澄清能力；防止模拟用户背答案 |
| 冲突 | C01–C10 在指定轮次注入（如：政府买服务≠买我们工具） | 测权衡与**证据边界**，不只测知识量 |
| 模式 | `learning` | 最接近「教练带半成品项目」 |

### B3. YL-R（竞赛评审 · 3 轮新会话）

| 项 | 设计 | 为什么 |
|----|------|--------|
| 材料 | 每轮新 session，粘贴**同一份**益量材料摘要 | 测**信息不足时**会不会编造 |
| 不给 Hidden | 评审侧不应「知道」访谈细节 | 专测边界感与评审结构 |
| 模式 | `competition` + 挑战杯 |

### B4. YL-S（压力测试）

| 项 | 设计 | 为什么 |
|----|------|--------|
| 输入 | 固定挑衅句（编市场规模、写虚假合作、扩到助餐志愿者） | 测**拒绝**与拉回 MVP |
| 用途 | 补 YL-G 里「不明显编造」的盲区 | 探索性发现：正常建议里编造比压力句更常见 |

### 测试世界（三类测试共用）

| 文档 | 作用 |
|------|------|
| 《项目完整背景》 | 可提交；只写问题与条件 |
| 《Hidden State》 | 仅 harness；条件披露 |
| 《冲突约束》 | 仅 harness；注入矛盾 |

**设计原则（页脚四行）**  
同一项目世界 · 信息分层披露 · 冲突测权衡 · V1/V2 同题对比

## P11 记录哪些变量、用于什么分析

**A. 内容里程碑（7 项）→ 分析：Agent 有没有推进「益量」本身**

| # | 里程碑 | 分析用途 |

**C. 工程遥测（每轮）→ 分析：慢在哪、环境是否可信**

- 延迟、API 错误、RAG 检索错误  
- 释放了哪些 Hidden 包、是否误释放

**D. 汇总分析怎么用**

| 分析问题 | 看哪些变量 |
|----------|------------|
| V1 冻结问题清单 | Outcome 漂移次数、编造条数、YL-G 重复模式 |

## P13 测试结果（一）：整体与工程面

**环境**：V1fix-A 为探索性；正式分数以 V1fix-B 为准。

| 维度 | 结果 |
|------|------|
| **能用的部分** | 能讲政策逻辑、能往项目收敛；压力句下对**显性编造**有一定拒绝；部分轮次能吸收学生纠正 |
| **工程面** | 约 **11–12 次**模型调用 / 用户轮；端到端延迟中位数约 **152 秒** |
| **和 P7 现象的对应** | 慢 ↔ 多维度并行；漂移/编造 ↔ Outcome 低 |

**讲稿**：不是「Agent 完全不能用」，而是「复杂题下，**可控性**不够」——所以值得做 V2，且必须用同一套尺量。
