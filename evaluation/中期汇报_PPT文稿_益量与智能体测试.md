## P5 为什么选这个题：政策与采购都是真的

**本页要点（事实 F，有公开依据）**

1. **政府购买服务**：按数量、质量等因素付费，强调预算与绩效（财政部《政府购买服务管理办法》）。  
2. **探访关爱**：要求识别需求、发现风险、转介衔接、注意隐私（国家专项指导意见）。  
3. **政府采购真实存在**：公开案例有探访关爱项目预算约 **42 万**、**67 万/6 个月** 等；街道级社区服务采购可达 **数百万/两年**。

**必须说清楚的一句话**

> 这些事实只证明「这类公共服务会被政府购买」；**不能**直接推出「政府会购买我们做的任何数字化工具」——后者仍是 **H（假设，待验证）**。

**讲稿要点**：选题有政策与采购锚点，避免空喊「养老大市场」；同时我们刻意区分「场域真实」和「我们的产品已被需要」。

## P10 为什么这样测是合理的：四个原则

**本页要点**

1. **同一项目、同一世界**  
   用《YL-Scenario Ground Truth》冻结益量场域；避免 V1 聊成「志愿者 App」、V2 聊成「助餐平台」——否则无法对比。

2. **信息分层，测「会不会问」**  
   公开背景 vs Hidden State：模拟用户**只有被问对才透露**细节；测澄清能力，不是测背稿。

3. **冲突注入，测「会不会权衡」**  
   例如：主管要详细 vs 一线怕多填；政府买服务 ≠ 政府买我们的工具——看智能体能否守住证据边界。

4. **前后对照，测「有没有真进步」**  
   V1 冻结问题清单 → 改智能体 → **同一套题**再跑；不挑最好的一次 run 汇报。

**讲稿要点**：这和软件回归测试一样：固定输入、固定环境、记录输出、版本对比。我们是在给 **Agent 做 harness（评测束具）**。

## P15 V1fix-A 测试结果（一）：整体印象

**本页要点**

**环境说明（必读）**  
探索性运行；存在模型切换未逐轮记录、个别会话网络污染剔除等情况——**数字供趋势判断，正式分数以 V1fix-B 为准**。

**做得好的地方**

| 方面 | 表现 |
|------|------|
| 基础辅导能力 | 能讲政策逻辑、项目收敛方向 |
| 安全底线 | 压力场景下对**明显编造**有一定拒绝 |
| 用户纠正后 | 部分轮次能吸收学生反驳并调整 |

**粗略工程观测**

- 约 **11–12 次**模型调用 / 用户轮（冻结日志统计）  
- 端到端延迟中位数约 **152 秒/轮**（与多维度并行编排相关）

**讲稿要点**：肯定「能聊」，但中期重点转向「聊得稳、聊得准、聊得快」。

## P16 V1fix-A 测试结果（二）：反复出现的问题

**本页要点（= V2 优化契约的输入）**

| 优先级 | 问题 | 典型表现 |
|--------|------|----------|
| P0 | **数字/事实编造** | 正常建议里凭空出现价格、规模、覆盖率（比压力测试更严重） |
| P0 | **最终总结漂移** | 多轮已收窄到「探访台账」，总结又变成语音/微信工具或换付费方 |
| P1 | **RAG 污染** | 检索命中无关案例（如其他赛道项目），干扰建议 |
| P1 | **提问泛滥** | YL-G 24/24 轮存在「一问多叠」，且常跨主题 |
| P2 | **延迟高** | 多维度 Path A/B 即使用户只问一个小点也可能跑满链路 |
| P2 | **遥测不全** | 对话 JSON 未稳定记录每轮实际模型 |

**初步评分趋势（0–4，探索性）**

| 测试 | Outcome 大致区间 |
|------|------------------|
| YL-G 三轮 | 约 **0–1**（收敛差、漂移多） |
| YL-S 压力 | 约 **3**（显性编造能挡一部分） |
| 理论/概念类 | 约 **2** |

**讲稿要点**：问题在多条测试里**重复出现**，所以适合写进「优化契约」，而不是怪某一次 prompt 手滑。

## P17 从测试到改进：我们准备优化什么（框架稿）

> ⏳ **本节待组内填入 V1fix-B 后定稿**；以下为实现方向框架，汇报时可讲「计划」。

**本页要点**

**智能体层（V2 内容优化，示例）**

- 提示词：证据边界、F/H/S 强制区分、总结前核对 `decisions`  
- 知识库：减少无关案例召回；探访/公益/政务分类  
- 拒绝策略：未验证数字、付费方、长期影响  

**编排层（减法式升级，不新增「世界状态 Agent」）**

| 方向 | 做法 |
|------|------|
| 共享状态 | `Project Runtime State`：memory / progress / **decisions** / tasks |
| 响应契约 | 综合前注入 `must_preserve`、`forbidden_upgrade` |
| 少调用 | 合并维度、按 `refresh` 跳过无关 KG/超图 |
| 快慢路径 | 关键回答先返回，重型面板后台刷新 |

**启用策略**：**影子验证**（用 V1 日志重放新判断）→ 再小流量真启用（见前期讨论）

**讲稿要点**：优化不是「再加功能」，而是「加控制平面 + 减无效调用」；等 V1fix-B 冻结后再报具体 commit 与对比数字。

## P20 总结：中期我们证明了什么

**本页要点**

1. **项目**：益量选题有政策与采购锚点，问题表述清楚，证据边界自律。  
2. **方法**：建立了可复现的 Agent harness，不是随意聊天。  
3. **基线**：V1 能辅导但存在漂移、编造、慢——问题可重复、可列清单。  
4. **方向**：V2 = 同一套测试下的可验证改进，而非重写题目或换赛道。

**一句话收尾**  
> 中期成果 = **选对了题** + **建对了尺** + **量清了 V1 的短板**；下一步用同一套尺证明 V2 真的更好。
